## 1. Wave Plan YAML/MD Schema Alignment

### P1-1: Wave Plan File Format Mismatch (P1)

**Files Involved**:
- `layers/L3-ARCHITECTURE/dag-router/_SKILL.md` (lines 405-479, 697-732)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 49, 74, 92, 120, 713-721)
- `layers/L2-ENGINE/executor/_SKILL.md` (lines 48, 90-107, 122)
- `layers/L3-ARCHITECTURE/parallel-engine/_SKILL.md` (lines 13, 72, 105, 120)

**Issue**: dag-router produces output as **`WAVE-PLAN.md` (Markdown)** at path `.ultimate-workflow/<req-id>/WAVE-PLAN.md`, while wave-executor and executor both expect input as **`wave-plan.yaml` (YAML)** at path `.ultimate-workflow/wave-plan.yaml`.

**dag-router Output** (line 475):
```bash
cat > .ultimate-workflow/<req-id>/WAVE-PLAN.md << 'EOF'
```

**wave-executor Input Expectation** (line 49):
```markdown
- [ ] Wave plan file exists at `.ultimate-workflow/wave-plan.yaml` (or specified path)
```

**executor Input Expectation** (line 122):
```bash
for task in $(yq '.wave_plan[] | select(.wave_number == '$WAVE_NUM') | .tasks[].id' wave-plan.yaml); do
```

**parallel-engine Description** (lines 7, 13, 105, 120): References `WAVE-PLAN.md` consistently — aligns with dag-router output format.

**Impact**: Downstream consumers have two different expectations for the same artifact's format and location:
- parallel-engine expects markdown (`WAVE-PLAN.md`) — matches dag-router
- wave-executor expects YAML (`wave-plan.yaml`) — does NOT match dag-router
- executor expects YAML (`wave-plan.yaml`) — does NOT match dag-router

**Recommendation**: Define a canonical Wave Plan schema format. Either:
1. Standardize on markdown (`WAVE-PLAN.md`): Update wave-executor and executor to read markdown, or
2. Standardize on YAML (`wave-plan.yaml`): Update dag-router's Step 3 output to generate YAML instead of Markdown. The YAML approach is recommended because it enables structured validation (JSON Schema) which wave-executor already defines (lines 707-717).

### P1-2: Wave Plan YAML Field Naming Inconsistency (P1)

**Files Involved**:
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 713-717, input schema validation table)
- `layers/L2-ENGINE/executor/_SKILL.md` (lines 90-107, YAML example)

**Issue**: The wave-executor's Input Schema Validation (lines 713-717) defines fields using the key `wave_plan[]`:

```
| Field | Type | Constraint |
| `wave_plan[].wave_number` | integer | ...
| `wave_plan[].tasks[].id` | string | ...
| `wave_plan[].tasks[].deps` | string[] | ...
| `wave_plan[].tasks[].priority` | enum | P0 / P1 / P2 only
| `wave_plan[].tasks[].type` | enum (optional) | coding/testing/review/config
```

But the executor's example (lines 93-107) uses a different top-level key:

```yaml
# wave_plan:
#   - wave_number: 1
#     tasks:
#       - id: auth-model
#         deps: []
#         priority: P0
#       - id: constants
#         deps: []
#         priority: P0
```

Both use `wave_plan` as top-level key and `tasks[].deps`, so the structure is consistent between these two. However, dag-router's template (lines 428-431) uses markdown table format with column names that don't map directly to YAML field names:

```markdown
| Task ID | Name | Depends On | Worktree | Shared Resources |
```

vs. the expected YAML fields: `id`, `name`, `deps` (implied), `worktree` (missing in YAML schema), `shared_resources` (missing in YAML schema).

**Recommendation**: The Wave Plan YAML schema must include ALL fields that dag-router outputs, specifically `worktree` and `shared_resources`, or dag-router must stop outputting them to its template.

### P2-1: Missing `worktree` and `shared_resources` in YAML Schema (P2)

**Files Involved**:
- `layers/L3-ARCHITECTURE/dag-router/_SKILL.md` (lines 428-431, 716-718 — template includes these fields)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 713-717 — validation table does NOT include them)

**Issue**: dag-router's WAVE-PLAN.md template includes `Worktree` and `Shared Resources` columns (line 428, 716), but the wave-executor's Input Schema Validation table (lines 707-717) defines only 5 fields (`wave_number`, `tasks[].id`, `tasks[].deps`, `tasks[].priority`, `tasks[].type`) and omits `worktree` and `shared_resources`.

**Impact**: If wave-executor validates against its schema, worktree assignments from dag-router will be silently dropped or cause validation errors.

**Recommendation**: Add to wave-executor's schema table:
```
| `wave_plan[].tasks[].worktree` | string | Non-empty path like "wt/{task-id}" | WARNING if missing — defaults to none |
| `wave_plan[].tasks[].shared_resources` | string[] | List of resource paths | WARNING if empty for HIGH parallelism waves |
```

## 2. Phase Artifact Transfer Consistency (Phase 0→8)

### P2-2: Task ID Naming Convention Mismatch Between Phase 3 and dag-router (P2)

**Files Involved**:
- `layers/L1-INTERACTION/phase-3-task-plan/_SKILL.md` (lines 84-92, template uses `T<NN>` format like T01, T02)
- `layers/L3-ARCHITECTURE/dag-router/_SKILL.md` (lines 96-115, example uses kebab-case IDs like auth-model, auth-service)

**Issue**: Phase 3's task template (line 84) specifies:
```markdown
### Task ID: T<NN>
```
with examples using `T01`, `T02` format. dag-router's example (lines 96-115) uses descriptive kebab-case IDs like `auth-model`, `auth-service`, `api-routes`.

**Downstream Impact**: wave-executor and executor reference task IDs in checkpoint heartbeats (`[checkpoint][wave:N][task:auth-model]`), dependency validation, and commit messages. If Phase 3 outputs `T01` but dag-router expects `auth-model`, there's a mapping gap.

**Recommendation**: Define a canonical Task ID format in Phase 3. Either:
1. Use kebab-case descriptive IDs (recommended — more human-readable, used by dag-router)
2. Keep T<NN> format but add a `task_name` or `identifier` field that dag-router maps from

### P2-3: Wave SUMMARY Schema Partial Mismatch Between Producer and Consumer (P2)

**Files Involved**:
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 293-346 — SUMMARY template)
- `layers/L2-ENGINE/executor/_SKILL.md` (lines 540-572 — SUMMARY template variant)
- `layers/L1-INTERACTION/phase-8-archive/_SKILL.md` (lines 102-113 — SUMMARY aggregation expects specific fields)

**Issue**: Three different wave SUMMARY templates exist with structural differences:

| Field | wave-executor | executor | phase-8-archive expectations |
|-------|---------------|----------|------------------------------|
| Success Rate format | `{passed}/{total} ({percentage}%)` | `{passed}/{total} ({percentage}%)` | Table cell counts (not percentage) |
| Tasks Executed label | "Tasks Executed" | "Tasks Executed" | "任务数" (Chinese) |
| LESSONS section | `## LESSONS Nomination` with bullet items | `## LESSONS Nomination` with L-XXX prefix | Plain text names without L-XXX prefix |
| Breaking Changes section | Present | Present | Implicit in aggregation table |
| Next Wave Dependencies | Detailed list format | Table with task status | Simple table cell |

**Impact**: phase-8-archive's aggregation (Step 1) expects a specific table format that doesn't match any of the three SUMMARY templates exactly. The aggregator reads markdown tables, but each producer writes slightly different column structures.

**Recommendation**: Define a canonical Wave SUMMARY schema at `layers/L2-ENGINE/wave-executor/_SKILL.md` and have executor and phase-8-archive conform to it. Remove redundant templates from executor (lines 540-572) and phase-8-archive (lines 106-113).

### P2-4: Phase 4 Consumption Path Ambiguity (P2)

**Files Involved**:
- `layers/L1-INTERACTION/phase-4-build/_SKILL.md` (lines 20, 34, 57)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (line 355 — writes to `.specs/waves/wave-{N}/SUMMARY.md`)

**Issue**: Phase 4 states (line 34):
```markdown
- **消费** `.specs/waves/wave-{N}/SUMMARY.md` — Wave Executor 写入的标准路径(不再产生自己的 WAVE-N-SUMMARY.md)
```

But phase-8-archive references (line 83):
```
Wave SUMMARY 引用统一为 `.specs/waves/wave-{N}/SUMMARY.md`,与 Phase 4/Phase 5/Wave Executor 一致。不再引用旧的 `WAVE-N-SUMMARY.md` 路径。
```

However, executor uses a different file for heartbeats — `dev-log.md` (line 125):
```bash
if ! grep -q "\[checkpoint\].*\[task:${dep}\].*✓" dev-log.md; then
```

And executor Step 1.9 (line 481) writes checkpoints to `dev-log.md`:
```bash
echo "[checkpoint][wave:${WAVE_NUM}][task:${TASK_ID}] ✓ (25min)" >> dev-log.md
```

But wave-executor (lines 360, 503) writes heartbeats to `.specs/waves/wave-{N}/heartbeat.log`.

**Impact**: Two different heartbeat log files (`dev-log.md` vs `.specs/waves/wave-{N}/heartbeat.log`) exist with no defined mapping or ownership. Phase 4's dependency verification in executor reads `dev-log.md` but wave-executor writes to `heartbeat.log`.

**Recommendation**: Standardize on `.specs/waves/wave-{N}/heartbeat.log` as the canonical heartbeat location. Remove or deprecate `dev-log.md` references from executor. Document which component owns which log file.

## 3. LESSONS.md Cross-Wave Injection Feedback Loop

### P3-1: Cross-Wave Injection Log Schema Alignment (P3)

**Files Involved**:
- `layers/L2-ENGINE/learning-workflow/_SKILL.md` (lines 527-533 — injection log template)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 314-320 — LESSONS nomination format)

**Issue**: learning-workflow defines the cross-wave injection log schema at lines 527-533:
```markdown
| injected_skill | wave_from | wave_to | success:bool | impact_score:1-5 | notes |
```

Required fields: `injected_skill`, `wave_from`, `wave_to`, `success` (boolean), `impact_score` (integer 1-5).

However, wave-executor's LESSONS nomination format (lines 314-320) uses:
```markdown
- **[NEW]** React useEffect Infinite Loop → Wave {N}, Task: user-profile
  - Root cause: Missing dependency array
  - Fix: Add `[userId]` to useEffect dependencies
  - Reusability: ⭐⭐⭐⭐ (common in React projects)
```

And executor's nomination format (lines 557-559):
```markdown
## LESSONS Nomination
- L-NEW [SUCCESS] bcrypt salt rounds 10 sufficient for most apps
- L-NEW [FAILURE] Missing type import causes TS2307
```

The nomination format doesn't directly map to the injection log schema — there's no `injected_skill`, `wave_from/to`, or `impact_score` in the nominations.

**Impact**: The bridge between LESSONS nomination (production) and cross-wave injection (consumption) is implicit rather than explicit. There's no structured data flow connecting these two phases.

**Recommendation**: Add a mapping step that converts LESSONS nominations into the injection log format. Ensure each nominated lesson includes:
- `injected_skill` = domain skill path or lesson ID (L-XXX)
- `wave_from` = source wave number
- `success` = boolean derived from [SUCCESS]/[FAILURE] tag
- `impact_score` = converted from reusability star rating

### P2-5: Lesson Numbering System Not Enforced Across Writers (P2)

**Files Involved**:
- `layers/L2-ENGINE/learning-workflow/_SKILL.md` (lines 243-319 — LESSONS template with L-XXX numbering)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 314-320 — nominations use [NEW] without L- prefix)
- `layers/L2-ENGINE/executor/_SKILL.md` (lines 557-559 — nominations use L-NEW prefix)

**Issue**: learning-workflow defines lesson numbering as `L-XXX` (3-digit zero-padded, lines 316-318):
```markdown
## L-XXX [FAILURE/SUCCESS/INSIGHT/PATTERN] {Short Title}
```
with numbering rules: "Format: `L-XXX` (3-digit zero-padded), Incremental only (never reuse numbers)"

But wave-executor nominations use `[NEW]` and `[UPDATE]` prefixes without L-XXX identifiers (lines 314-320). executor uses `L-NEW` format which conflicts with the expected `L-042` format.

**Impact**: When multiple waves nominate lessons concurrently or out of order, numbering collisions occur because there's no enforced sequential counter across all writers.

**Recommendation**: Standardize on L-XXX format across all writers. The [NEW]/[UPDATE] tags from wave-executor should be converted to proper L-XXX numbers during the LESSONS.md write step in learning-workflow (Step 2).

## 4. Wave Plan YAML File Consistency Across Components

### P1-3: parallel-engine vs wave-executor Parallelism Classification Inconsistency (P1)

**Files Involved**:
- `layers/L3-ARCHITECTURE/parallel-engine/_SKILL.md` (lines 628-634 — Parallelism-to-Merge mapping)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (lines 244-251 — Parallelism Strategy table)

**Issue**: parallel-engine and wave-executor define different mappings for the same parallelism levels:

| Level | parallel-engine definition | wave-executor definition |
|-------|---------------------------|--------------------------|
| HIGH | Independent worktrees (`wt/{task-id}`) | "All tasks truly parallel" |
| MEDIUM | Lock-based coordinated write, last-write-wins | "Serial DDL migrations, parallel DML operations" |
| LOW | Sequential commit, no merge needed | "Serial interface definitions, parallel implementations" |
| NONE | Atomic commit (single task) | "Force serial execution" |

These are **semantically different** — wave-executor's MEDIUM means "serial DDL + parallel DML" while parallel-engine's MEDIUM means "coordinated merge with locks". This suggests the two components have different mental models for what MEDIUM parallelism entails.

**Impact**: If dag-router classifies a wave as MEDIUM, parallel-engine will use lock-based coordinated merge while wave-executor expects serial DDL + parallel DML — these conflict if the wave contains both DDL and DML tasks.

**Recommendation**: Consolidate the parallelism classification definition into a single canonical location (recommend `layers/L3-ARCHITECTURE/parallel-engine/_SKILL.md` as it's the scheduling layer) and have wave-executor defer to it. Create a reference table that maps each level to a single, unambiguous strategy.

### P2-6: priority Field Not in dag-router Output Template (P2)

**Files Involved**:
- `layers/L3-ARCHITECTURE/dag-router/_SKILL.md` (lines 95-115 — input format example includes `depends_on`)
- `layers/L3-ARCHITECTURE/dag-router/_SKILL.md` (lines 428-431, 716-718 — output template lacks `priority`)
- `layers/L2-ENGINE/wave-executor/_SKILL.md` (line 52, 716 — requires priority P0/P1/P2)

**Issue**: dag-router's input format example (lines 95-115) shows tasks with:
```yaml
tasks:
  - id: auth-model
    name: "Create User authentication model"
    depends_on: []
    shared_resources: ["src/models/"]
```

But there is NO `priority` field. dag-router's output template (lines 428-431, 716-718) also lacks a `priority` column in the markdown tables. However, wave-executor's prerequisite gate (line 52) checks:
```markdown
- [ ] Task priorities assigned (P0/P1/P2) — no unassigned tasks
```

And wave-executor's input schema (line 716) requires:
```
| `wave_plan[].tasks[].priority` | enum | P0 / P1 / P2 only | FAIL |
```

**Impact**: If dag-router doesn't assign priorities to tasks, wave-executor's prerequisite gate will fail on every execution.

**Recommendation**: Add a `priority` field to dag-router's task processing. Options:
1. Auto-assign based on dependency depth (depth 0 = P0, depth 1 = P1, etc.)
2. Accept priority from Phase 3 task plan if present in `03-tasks.md`
3. Add explicit priority column to WAVE-PLAN.md template

## Methodology

- **Wave Plan Schema Alignment**: Checked all 4 core files (dag-router, wave-executor, parallel-engine, executor) for field name consistency and format compatibility in their definition/usage of `wave-plan.yaml` / `WAVE-PLAN.md`
- **Phase Artifact Transfer**: Traced data flow from Phase 3 output (`03-tasks.md`) through dag-router → Wave Executor → SUMMARY → Phase 8 archive, checking field continuity at each boundary
- **LESSONS Feedback Loop**: Verified that lesson nomination (Phase 8) and cross-wave injection (LearningWorkflow) share compatible schemas with the required fields: `injected_skill`, `wave_from`, `wave_to`, `success`, `impact_score`
- **File Format Consistency**: Checked that file format expectations match between producers and consumers across all components
