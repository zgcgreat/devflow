# Phase 1: 5 Whys需求追问

> **门控**: G1 (Plan Quality Gate) — 所有需求项有明确验收标准 → 通过
> **Layer**: Layer 1
> **适用模式**: Standard（条件跳过）, Strict（必跑）
> **前置产物**: `01-analysis.md`

---

## 📋 使用 5 Whys 方法穷追模糊表述

- "用户说'要快'——多快？具体指标是什么？"
- "支持'多种支付方式'——列出来，每种的技术复杂度？"

---

## ⚡ v3.2 交互流程

### 第1步：批量展示所有需要澄清的需求项

```
=== Phase 1: 需求澄清 ===

检测到以下模糊需求项需要澄清：

[1/3] ● 明确性能指标
[2/3] ○ 明确支持的支付方式
[3/3] ○ 明确用户体验要求

─────────────────────────────

现在逐项澄清：
```

### 第2步：逐项提问，每项提供预设选项

```
问题 1/3：明确性能指标

你提到"要快"——具体指标是什么？

  [A] 页面加载 < 1秒
  [B] 页面加载 < 3秒（可接受）
  [C] API 响应 < 200ms
  [D] 操作流程 < 3步完成
  [E] 其他自定义指标（直接输入）

  或选择多个（输入多个字母，如 AC）：
```

### 第3步：用户回答后更新进度，继续下一项

```
✅ [1/3] ● 性能指标 → 用户选 A + C

[2/3] ● 明确支持的支付方式
[3/3] ○ 明确用户体验要求

─────────────────────────────

问题 2/3：明确支持的支付方式

项目需要支持哪些支付方式？

  [A] 微信支付
  [B] 支付宝
  [C] 银行卡/信用卡
  [D] 货到付款
  [E] 其他（输入自定义）

  或选择多个（输入多个字母）：
```

### 第4步：全部澄清完毕后生成 `01-analysis.md`

```
✅ Phase 1 完成 — 所有需求项已澄清

澄清汇总：
1. 性能指标：A + C → 页面加载 < 1秒, API 响应 < 200ms
2. 支付方式：A + B + C → 微信 + 支付宝 + 银行卡
3. 用户体验：B → 操作流程 < 3步

已生成：`.forgeos/<req-id>/01-analysis.md`

请确认或输入 /skip 跳过 Phase 1（仅 Standard 模式可条件跳过）：
```

**目标**: 需求精确到可执行程度，每个需求项有明确验收标准。

---

## ⚠️ Phase 1 条件跳过规则（Standard 模式）

满足任意 **2项即可跳过**：

- ✅ 需求有明确验收标准（用户说"排版乱"且指向具体组件）
- ✅ 技术方案无歧义（不涉及技术选型决策）
- ✅ 影响范围可控（仅前端展示层，不涉及后端/数据）
- ❌ 需求包含"支持XX"但未列具体项 → 必跑5Whys追问

**跳过时的替代动作**：直接用用户需求生成简版 `01-analysis.md`（AC列表 + 影响范围）。

## Phase 1b: 决策捕获 (Discuss)

> **门控**: G2.5 (Decision Clarity Gate) — 决策覆盖率 ≥70% → 通过
> **Layer**: Layer 1 → Layer 2
> **触发条件**: AC包含≥3个技术选型歧义 / 用户要求"/discuss"模式

### ⚡ v3.2 提问交互流程

**第1步：批量展示所有待决策项**

```
=== Phase 1b: 技术决策捕获 ===

检测到以下技术决策需要确认：

[1/4] ● API 设计
[2/4] ○ 数据存储
[3/4] ○ 状态管理
[4/4] ○ 错误处理

─────────────────────────────

现在逐项确认：
```

**第2步：逐项提问，每项提供预设选项+优缺点**

```
问题 1/4：API 设计

请选择 API 架构风格：

  [A] RESTful — 标准HTTP方法，生态成熟，学习成本低
  [B] GraphQL — 灵活查询，避免过度/不足获取，学习曲线陡峭
  [C] gRPC — 高性能，强类型契约，调试工具链不成熟
  [D] 混合模式 — REST + gRPC（内部服务间用gRPC）

  或输入自定义方案（直接打字，发送后进入下一题）：
```

**第3步：用户回答后更新进度，继续下一题**（同上模式，逐项确认）

**第4步：全部决策完毕后生成 `CONTEXT.md`**

```
✅ Phase 1b 完成 — 技术决策全部确认

决策汇总：
1. API 设计：A → RESTful
2. 数据存储：C → IndexedDB + 封装库
3. 状态管理：B → Context API + useReducer
4. 错误处理：A → 立即提示 + 重试3次

已生成：`.forgeos/<req-id>/CONTEXT.md`

请确认或输入 /skip 跳过 Phase 1b：
```

### G2.5 门控规则

- ✅ 决策覆盖率 ≥70% → 通过
- ✅ 所有未决项标注 [NEEDS CLARIFICATION] → 通过
- ✅ CONTEXT.md格式正确 → 通过

**⚠️ 关键约束**: CONTEXT.md将作为Phase 2方案设计的约束条件，确保设计方案符合用户偏好。

### 常见歧义领域

| 领域 | 典型选项 |
|------|---------|
| API设计 | REST vs GraphQL vs gRPC |
| 数据存储 | localStorage vs IndexedDB vs SessionStorage |
| 状态管理 | Redux vs Context API vs Zustand |
| 错误处理 | 立即提示 vs 静默重试 vs 降级方案 |
| UI布局 | 单列 vs 双列 vs 响应式 |
| 认证方式 | JWT vs Session vs OAuth |

### Spec-Driven Development (SDD) 可选增强

如果用户需求复杂或涉及架构变更，可启用SDD模式：

```bash
/forgeos spec define "需求描述"    # 生成 specs/XXX/spec.md
/forgeos spec plan "技术描述"      # 生成 specs/XXX/plan.md
/forgeos spec tasks                # 生成 specs/XXX/tasks.md
```

SDD完成后自动生成CONTEXT.md，然后进入Phase 2。
