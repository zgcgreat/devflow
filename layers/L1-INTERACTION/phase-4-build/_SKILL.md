# Phase 4: 实施 (Wave 并行执行)

> **Layer**: L1-INTERACTION (SuperCorp 交互层) → Layer 2 SEP Engine 介入
> **前置产物**: `03-tasks.md` (Phase 3 通过 G4)
> **前置产物(消费)**: `.specs/waves/wave-{N}/SUMMARY.md` (Wave Executor L2-ENGINE 写入,Phase 4 直接消费)
> **后置产物**: Phase 4 自身不写 summary,仅编排和消费;最终汇总在 Phase 8 archive
> **门控**: G4-PHASE4 — Integration Gate（Phase 5/6/7/8 前置）

## 输入

- `03-tasks.md` — 任务拆分 + Wave 分组建议
- `.ultimate-workflow/STATE.md` — 当前执行状态
- LESSONS.md — 过往实施经验
- Phase 1-3 生成的所有前置产物（按需加载）

## 输出

- 按 Wave 分组执行的代码变更
- **消费** `.specs/waves/wave-{N}/SUMMARY.md` — Wave Executor 写入的标准路径(不再产生自己的 WAVE-N-SUMMARY.md)
- `[phase:orchestrator][wave:N][delegated-to:wave-executor]` — Phase 4 编排心跳

## ⚠️ 职责边界说明

**Phase 4 Build (L1-INTERACTION)** = 编排层: 决定"做什么、按什么顺序做",不直接写代码。
**Wave Executor (L2-ENGINE)** = 执行层: 负责"怎么做完",包含 Kahn 拓扑排序、心跳、summary 写入。

> **修复 (2024-05-17)**: Phase 4 已退化为纯编排器,所有实际执行逻辑委托给 Wave Executor。Phase 4 不再写自己的 summary(消除双重写入),直接消费 `.specs/waves/wave-{N}/SUMMARY.md`。

## 执行流程

### Step 0: Brownfield Detection (Pre-Wave Analysis)

Before executing waves, detect existing codebase state to handle incremental changes:

1. **Check for git status**: `git status --short` — any uncommitted changes in target directories?
2. **Checksum verification**: If `.specs/checksums/` exists, compare against current files
3. **Conflict detection**: Flag files that exist but differ from expected baseline
4. **Strategy selection**:
   - Clean room (no prior state) → Standard execution
   - Brownfield (existing codebase) → Delta Specs mode, backup modified files before overwrite

Output: `.ultimate-workflow/brownfield-report.md` with conflict list and recommended strategy.

### Step 1: Phase 3→Wave Plan Converter

在波执行开始前,将 Phase 3 的 Markdown 任务文件(`03-tasks.md`)转换为 Wave Executor 需要的 `wave-plan.yaml`。此步骤必须在 Wave 编排之前完成,是 Phase 4 的入口网关。

**输入**:
- `.ultimate-workflow/<req-id>/03-tasks.md` — Phase 3 输出的 Markdown 任务定义文件
- (读取) `.specs/waves/` — 确认是否已有旧版 `wave-plan.yaml` 可覆盖

**输出**:
- `.ultimate-workflow/wave-plan.yaml` — Wave Executor 的标准 YAML 格式,结构如下:

```yaml
# wave-plan.yaml — Auto-generated by Phase 3→Wave Plan Converter
# Source: 03-tasks.md (Phase 3 Task Plan output)
# Generated At: {ISO-8601 timestamp}
wave_plan:
  - wave_number: N
    tasks:
      - id: "{task-id}"
        name: "Task description (Chinese or English)"
        deps: ["{dep-task-id}", "{other-dep}"]    # empty [] if no deps
        priority: P0 | P1 | P2                     # critical / high / normal
        verify: "<shell command to verify the task>"
        done_criterion: "How to judge completion"
    parallelism: true    # true = no inter-task deps within this wave
```

**转换逻辑**:

1. **解析 `03-tasks.md` 中的 Task 段落**:按 `### Task ID:` 标记分割文件,提取每个任务的字段。Phase 3 输出格式示例:
   ```markdown
   ### Task ID: T01
   **描述**: 创建用户认证数据库模型
   **前置**: []
   **Read Files**: [src/models/base.py]
   **Write Files**: [src/models/auth.py, migrations/001_initial.sql]
   **Verify**: `pytest tests/test_auth_model.py -v`
   **Done 判定**: 所有认证相关模型可通过编译且单元测试全部通过
   ```

2. **解析 Wave 分组**:识别文件中的 Wave 标题(`Wave N1`, `Wave N2`等)和组内任务列表。Phase 3 输出示例:
   ```markdown
   ### Wave N1: 基础模块
   - T01, T02
   
   ### Wave N2: API 层
   - T03
   ```

3. **字段映射**:
   
   | Phase 3 (Markdown) 字段 | wave-plan.yaml 字段 | 转换规则 |
   |--------------------------|---------------------|----------|
   | `Task ID: TNN` | `tasks[].id` | 直接使用 Task ID 字符串 |
   | `描述`: XXX | `tasks[].name` | 取"描述:"后的值,去除多余空白 |
   | `前置`: [TXX] 或空 | `tasks[].deps` | 解析括号内任务ID列表;空→`[]` |
   | 无显式优先级字段 | `tasks[].priority` | 默认 `P1`;若描述含"核心/关键/Critical"→`P0`;若含"优化/改进"→`P2` |
   | `Verify`: `<cmd>` | `tasks[].verify` | 直接使用 Verify 命令原文 |
   | `Done 判定`: XXX | `tasks[].done_criterion` | 直接使用 Done 判定内容 |

4. **优先级自动推断规则**:
   
   | 关键词匹配(大小写不敏感) | 分配优先级 |
   |--------------------------|-----------|
   | "核心", "关键", "Critical", "Foundation", "基石" | P0 |
   | (无匹配) | P1 |
   | "优化", "改进", "Refactor", "Cleanup" | P2 |

5. **并行度标记**:同一 Wave 内若有 ≥2 个任务且所有任务的 `deps` 均为空→`parallelism: true`;否则→`parallelism: false`。

**转换前验证**:
- [ ] `03-tasks.md` 存在且非空
- [ ] 文件中包含至少一个 Wave 分组标记(`Wave N` 或 `### Wave`)
- [ ] 每个 Task ID 唯一(无重复)
- [ ] 所有前置依赖引用了存在的任务ID(无悬空引用)

**转换后验证**:
- [ ] `wave-plan.yaml` 可被 `yaml.safe_load()` 无异常解析
- [ ] `wave_plan` 数组非空且至少包含一个 wave
- [ ] 每个 wave 的 `wave_number` 从 1 开始连续编号(1,2,3,...)
- [ ] 所有任务有优先级(`P0/P1/P2`)
- [ ] 依赖图无环(Kahn 算法在 Wave Executor Step 1 中二次验证)

**示例 — 输入(`03-tasks.md`)**:
```markdown

### Task ID: T01

**前置**: []
```

**示例 — 输出(`wave-plan.yaml`)**:
```yaml

# Generated At: 2026-05-18T12:00:00Z
wave_plan:
```

**实现方式**:
- Wave Executor 在 Step 1 中用 Python/JavaScript/Shell 脚本读取 `03-tasks.md` 并生成 `wave-plan.yaml`
- 脚本需处理 Markdown 解析、字段映射、优先级推断和 YAML 序列化
- 生成的 `wave-plan.yaml` 写入 `.ultimate-workflow/wave-plan.yaml`(与 Wave Executor 预检门控的路径一致)

### Step 2: 编排 Wave N (委托给 Wave Executor)

1. 读取 `.ultimate-workflow/wave-plan.yaml`(Step 1 生成的转换产物),提取 Wave N 的所有 Task,构建任务图
2. **调用** Wave Executor (`layers/L2-ENGINE/wave-executor/_SKILL.md`),传入:
   - Task 列表 + 依赖关系
   - Verify 命令
   - Commit 格式要求
3. Phase 4 记录: `[phase:orchestrator][wave:N][delegated-to:wave-executor]`

### Step 3: 消费 Wave Executor 结果

1. 读取 `.specs/waves/wave-{N}/SUMMARY.md`(Wave Executor 写入)
2. 确认 Verify 通过率、Commit hashes、Lessons learned
3. 如果 G4-PHASE4 gate PASS → 编排 Wave N+1
4. 如果 G4-PHASE4 gate FAIL → 创建修复 Task,退回对应 Wave

### Step 4: LearningWorkflow 聚合 (Phase 完成后)

所有 Wave 执行完毕后,**统一触发** LearningWorkflow(仅一次):
1. 扫描 `.specs/waves/wave-{N}/SUMMARY.md` 中所有 LESSONS Nomination
2. 聚合到全局 LESSONS.md(L-NNN 格式)
3. 高频重复经验（≥ 3 次）→ 提名 Domain Skills Promotion

> **修复 (2024-05-17)**: Phase 4 不再每 Wave 都触发 LearningWorkflow(避免与 Phase 8 archive 冲突),由 Orchestrator 统一聚合。

### Step 5: PartyMode 共识（复杂决策时触发）

当 Phase 4 遇到需要跨 Agent 共识的决策：
1. 识别决策点（技术选型冲突、架构权衡）
2. 激活 PartyMode 多 Agent 讨论
3. 投票达成共识（>70% 一致或加权平均分 ≥ 75%）
4. 记录决策到 DECISIONS.md

## G4-PHASE4 门控检查（Phase 4→5）

| 检查项 | 通过条件 | 失败处理 |
|--------|---------|----------|
| Commit 原子性 | 每个 commit 对应单个 Task | 合并/拆分 commit |
| Verify 通过率 | Wave 内所有 Task verify 100% 通过 | 回滚未通过 Task 的 commit |
| Heartbeat 完整性 | 每个 Task 有 START+DONE 心跳 | 补跑缺失 Task |
| LESSON 提名 | Phase 失败任务已提名到 LESSONS.md | 自动创建 L-NNN 条目 |

## Error Taxonomy (Phase 4 Build 专属)

| Level | Name | Symptom | Recovery Action | Wave Impact |
|-------|------|---------|-----------------|-------------|
| P0 | VERIFY_FAIL_CRITICAL | Task verify command exits non-zero after retries | Rollback commit → fix → re-run verify | Blocks this task; dependent tasks in same wave blocked too |
| P1 | TASK_TIMEOUT | Heartbeat exceeds threshold (no START/DONE pair) | Cancel execution, kill subprocess, restart with fresh context | Retry once; if still fails → P0 |
| P2 | VERIFY_WARNING | Lint/type errors but runtime passes | Document warning, proceed, fix before Wave complete | Continue; blocked only if >5 warnings |
| P3 | CONTEXT_PRESSURE | Agent approaching 180K token limit (of ~200K) | Auto-trim CODE-BASE section, compress LESSONS to <5K tokens | No impact on execution |

## Boundary Conditions (Phase 4 Build)

### Thresholds
- **Per-Task Timeout**: ≤30 min per task (Wave N total ≤60 min)
- **Verify Retry Chain**: attempt_1: 5s → attempt_2: 10s → attempt_3: 20s + jitter(0-3s), then P0 rollback
- **Max Concurrent Tasks**: 7 recommended / 10 hard limit per wave (HIGH parallelism)
- **Commit Atomicity**: Single commit per task, `<type>(<req-id>): <task-id> <subject>` format

### Circuit Breaker
- 3 consecutive P0 failures on same file → OPEN circuit, route to Phase 6 Specialist review
- Wave total failure rate >50% → recommend re-split tasks in Phase 3

### Input Schema Validation
- [ ] `03-tasks.md` exists and has G4 passed
- [ ] All tasks have verify command + done criterion defined
- [ ] Worktree assignments match parallelism level (HIGH→per-task, LOW→shared)
- [ ] No circular dependencies in DAG (Kahn algorithm completed)

- Phase 4 → **高代码能力模型**（Execution Agent）
