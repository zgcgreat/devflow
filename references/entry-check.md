# 入场检测详细规则 ⭐v3.2

> 本文件是 GO.md 第二步的详细展开，由 GO.md 按需加载。
> **v3.2 更新**: 选择题交互模式 + 情况 G（已有外部上下文）、模式适配规则（Fast/Lean/Standard/Strict）

## 强制门控

入场检测是**进入任何需求相关阶段的前置门**。未完成本步检测前，AI **禁止**进入以下任一阶段：
- 0-confirm（需求确认）
- 1-analysis（需求分析）
- 2-design（方案设计）
- 文档解析模式（D.1/D.2/D.3）

**例外**：横向命令（A-architect / A-evolve / I-intel-scan / L-restyle / M-health）不跑本步。

---

## 决策树（按顺序判定，命中即停止）

```
1. STATE.md 有 ai_context_doc 字段？
   └─ 是 → 情况 A（直接用指定文档）
   └─ 否 → 继续

2. .forgeos/memory/CONTEXT.md 存在？
   ├─ 存在且 last_intel_scan < 90天 → 情况 B（直接用）
   ├─ 存在且 last_intel_scan > 90天 → 情况 C（提醒可重扫）
   └─ 不存在 → 继续

3. 检测到其他 AI 上下文文档？
   └─ 是 → 情况 D（停等用户确认用哪个）
   └─ 否 → 继续

4. 检测到外部上下文（.workbuddy/memory/ 等）？⭐v3.1新增
   └─ 是 → 情况 G（复用外部上下文）
   └─ 否 → 继续

5. 项目是 greenfield？
   └─ 是 → 情况 F（跳过）
   └─ 否 → 情况 E（停等用户确认）
```

### 情况 G · 检测到外部上下文（已有 .workbuddy/memory/ 等）⭐v3.1新增

**判定条件**：`.forgeos/memory/CONTEXT.md` 不存在 **且** STATE.md 无 `ai_context_doc` 字段 **且** 未检测到标准 AI 上下文文档 **且** 检测到以下任一外部上下文：
- `.workbuddy/memory/MEMORY.md`（WorkBuddy 工作记忆）
- `.workbuddy/memory/YYYY-MM-DD.md`（WorkBuddy 日志）
- `CLAUDE.md`（Claude Code 项目上下文）
- `.cursor/rules/`（Cursor 规则）
- 项目根 `README.md` 含项目技术栈描述

**动作**：**复用外部上下文，不跑 intel-scan**。将外部上下文路径记录到 STATE.md，后续阶段直接读取。

**检测结果框**：
```

│  🔍 入场检测                                                  │

│  检测结果：情况 G ⭐v3.1                                     │
│  项目类型：brownfield                                         │
│  上下文文档：<外部上下文路径列表>                              │
│  入场扫描状态：已跳过（复用外部上下文）                        │
└─────────────────────────────────────────────────────────────┘
```

**更新STATE.md**：
- `项目类型`: brownfield
- `入场扫描状态`: 已跳过
- `上下文文档`: <外部上下文路径列表>
- `跳过原因`: 复用已有外部上下文（情况G）

**设计理由**：brownfield 项目通常已有 .workbuddy/memory/ 或 CLAUDE.md 等工作记忆，这些上下文比 intel-scan 生成的 CONTEXT.md 更鲜活（随日常开发持续更新）。强行重跑 intel-scan 既浪费 token 又可能覆盖更有价值的信息。

---

## 为什么这步重要

跳过会导致：
- AI 不知项目架构 → 写出不合项目风格的代码
- AI 重复实现已有抽象 → 费 token 且产生重复代码
- 4-dev 的 schema 任务 / 破坏性变更检测都会不准
- 用户明明有 CLAUDE.md 写好的约定 → AI 完全不读 → 抱怨"为什么不按我说的来"

## 模式适配规则 ⭐v3.1

入场检测的执行深度与模式挂钩，避免小任务被强制跑完整检测。

| 模式 | 入场检测行为 | 说明 |
|------|-------------|------|
| **Fast** | ⏭️ 跳过 | 1~2文件改动无需项目上下文，AI 直接看代码即可 |
| **Lean** | ✅ 简化 | 复用已有外部上下文（情况 G 优先），不跑 intel-scan；仅确认上下文来源 |
| **Standard** | ✅ 完整 | 按决策树完整执行，情况 D/E 必须停等用户 |
| **Strict** | ✅ 完整 + 强制 | 按决策树完整执行，所有情况都需要输出检测结果框 |

### Lean 模式入场检测流程

```
1. 检查 .workbuddy/memory/MEMORY.md → 有 → 情况 G（直接用）
2. 检查 CLAUDE.md / .cursor/rules/ 等 → 有 → 情况 G（直接用）
3. 检查 .forgeos/memory/CONTEXT.md → 有 → 情况 B/C（按原规则）
4. 都没有 → 输出简短提示"Lean模式：无项目上下文，直接看代码"，继续
```

**Lean 不需要停等用户确认**，因为 3~5 文件改动风险可控，且用户需求已明确。

### Fast 模式入场检测

Fast 模式直接跳过入场检测，在路由声明中标注"Fast: 跳过入场检测"即可。

**理由**：Fast 改动范围极小（1~2 文件、<50 行），不需要项目级上下文；AI 直接读取目标文件即可理解改动范围。
