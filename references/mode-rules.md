# 模式判定与切换规则（详细）

> 本文件是 SKILL.md 模式部分的详细展开。
> **v3.2**：四档模式（Fast/Lean/Standard/Strict）+ 选择题交互模式

## Fast 模式准入 Checklist

**进入 Fast 模式前，AI 必须确认以下所有条件：**

### 硬性指标（必须全部满足）

- 改动文件数 ≤ 2
- 预估代码行数 < 50（不含空行/注释）
- 不涉及数据库 schema 变更
- 不涉及 API 接口签名变更
- 不涉及鉴权/权限/支付逻辑

### 软性指标（至少满足 3/5 项）

- 需求描述清晰无歧义
- 有明确的验收标准
- 不影响其他模块（非公共组件）
- 有现成的测试框架可直接运行
- 非核心业务逻辑

### 自动排除项（命中任一项 → 升级）

- 修改订单/支付/用户认证核心逻辑
- 修改公共组件/工具函数（被多处引用）
- 涉及第三方依赖版本升级
- 需要修改 CI/CD 配置
- 需要数据迁移或回滚方案

### Fast 检查输出格式

AI 在判定 Fast 模式时，必须输出检查结果：

```
🔍 Fast 模式检查

硬性指标:
✅ 改动文件数: 1个
✅ 预估行数: 30行
✅ 无schema变更
✅ 无API变更
✅ 非鉴权逻辑

软性指标:
✅ 需求清晰
✅ 有验收标准
❌ 影响其他模块
✅ 有测试框架
✅ 非核心逻辑

结果: 5/5硬性通过，4/5软性通过
判定: ✅ 符合 Fast 模式
```

如软性指标 < 3/5，输出警告并推荐升级。

---

## Fast → Lean/Standard/Strict 切换

如果用户反对或 AI 发现隐藏风险（如改动超预期、涉及 schema 等），**必须暂停并输出模式切换确认**：

```
⚠️ Fast 模式切换为 <Lean/Standard/Strict>
   触发原因：<具体原因>
   新流程：<对应模式的流程>

   是否同意切换？[Y/n]
```

- ⭐v3.1 优先推荐 Lean（改动 3~5 文件、50-300 行、不涉及架构）而非直接跳到 Standard。
- 用户确认后才可切换，AI 不得自行切换。

---

## Lean → Standard 升级条件（命中任一即升级）

- 实际改动文件数 > 5
- 涉及架构/数据模型变更
- 需求模糊需要追问
- 用户要求更严格的审查

---

## 模式降级评估（阶段切换时评估，需用户确认）

| 信号 | 当前模式 | 可降级到 |
|---|---|---|
| 实际改动文件数 ≤ 2，且均为同一层 | Standard | Fast |
| 实际改动文件数 3~5，不涉及架构/数据模型 | Standard | Lean |
| 所有改动 < 50 行 | Standard | Fast |
| 所有改动 50-300 行，不涉及架构/数据模型 | Standard | Lean |
| 无数据库/API/跨模块影响 | Standard | Fast 或 Lean |
| 用户表示"太多了/太复杂了" | **任何模式** | 降一级或暂停 |

降级前暂停并询问：

```
📉 建议模式降级：Standard → <Fast/Lean>
   触发信号：实际改动仅 N 文件 M 行
   裁剪内容：跳过 2-design / 2a-ui-design
   是否同意降级？[Y/n]
```

---

## 高风险自动升级 Strict

命中以下任一关键词自动升级到 Strict：

- 鉴权、权限、支付、账单
- secret、PII、数据保留
- schema / migration
- 公共 API / SDK
- infra、部署、CI/CD、环境配置
- 依赖升级、跨模块架构
- 并发、后台任务、缓存
- 数据丢失风险、不可逆操作
- 上线回滚敏感路径

---

## 风险评估矩阵

| 维度 | 低 (1分) | 中 (2分) | 高 (3分) |
|---|---|---|---|
| **技术复杂度** | 简单CRUD、单文件修改 | 多文件协调 | 新算法/协议、分布式系统 |
| **业务影响** | 内部工具、非核心功能 | 用户-facing功能 | 支付/订单/鉴权 |
| **数据敏感性** | 无持久化 | 普通业务数据 | PII、金融数据、密钥 |
| **回滚难度** | 代码回退即可 | 需数据迁移但可逆 | 不可逆操作 |

### 评分规则 ⭐v3.1

```
总分 = 各维度得分之和（最高12分）

总分 1-2   → Fast
总分 3-4   → Lean
总分 5-7   → Standard
总分 8-12  → Strict

如果任一维度为"高"或总分 ≥8 → 强制 Strict
```

### 特殊规则

1. **一票否决**：任一维度为"高"且涉及支付/金融交易、用户认证、数据库schema变更、生产部署 → 强制 Strict
2. **保守策略**：置信度 < 60% → 建议升级到更高级模式
3. **用户覆盖**：用户可显式指定模式覆盖AI推荐，但AI必须记录风险提示

## Fast 路由声明要求

Fast 路由声明必须包含：

```
✅ 模式：Fast
✅ 改动范围：<文件列表>
✅ verify 命令：<具体命令>
✅ 预期结果：<通过标准>
```

---

## Lean 路由声明要求

Lean 路由声明必须包含：

```
✅ 模式：Lean
✅ 改动范围：<文件列表，3~5个>
✅ 轻量方案：<1段描述，说明改什么、怎么改>
✅ verify 命令：<具体命令>
✅ 预期结果：<通过标准>
```

---

## 用户显式跳过

用户说"跳过设计" / "不要写需求" → 允许跳过，但 AI 必须在路由声明中记录：
- 跳过了什么
- 跳过的原因
- 后续阶段发现问题时不得以"没走过设计"为借口

---

## 例外情况

用户在需求中已显式指定模式（如"Fast 模式：修个 typo"）→ 可直接采用，但仍要在路由声明中展示该模式和流程。
